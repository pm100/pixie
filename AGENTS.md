# Agent instructions

- Never commit or push unless the user says so.
- Only pluralise when a count is more than one: "1 item", "2 items" (use `plural` in `ui/src/lib/format.ts`).
- Always keep builds clean: no compiler warnings (cargo check --workspace --all-targets). Fix new ones straight away rather than leaving them; do not silence them with `#[allow]`. Delete dead code, or gate it (`#[cfg(...)]`) when only one platform or the tests use it.
- When dependencies change (Cargo.toml, ui/package.json, the vcpkg libraries or the downloaded models), run `just notices` and commit THIRD-PARTY-NOTICES.md and ui/src/generated/third-party.json; Settings, About lists them.
- Buttons: white by default; `class="primary"` (blue) for the one main action of a screen, dialog or panel; `class="danger"` (red) for actions that delete or reset things. The styles are global (`ui/src/App.svelte`): do not restyle buttons per component. Blue as a "selected" state (the active tab, a picked tick) is separate from the button style. A button label is one or two words ("Keep new", "Discard", "Done"): put counts and detail in the text beside it and the rest in the tooltip, not on the button.
- Never put a control in the middle of a sentence in the UI (e.g. "Refresh every [nn] days"): word order differs between languages, so it cannot be localized. Use a label followed by the control instead: "Days between refreshes: [nn]". The prompts that had this (Email, Network folders, Trips and Recent days in Settings) were fixed in #73; check any new settings text for it, and put units in the label ("Distance (km):") rather than after the control.
- A page or tool pane takes its inner margin from `--page-pad` (or `--page-pad-y` / `--page-pad-x` where a header runs edge to edge), defined once in `ui/src/App.svelte`: do not write its own padding numbers.
- A popup (modal window) never resizes while the person is using it: people find it distracting. Give it one fixed size that fits its busiest screen, keep its buttons at the bottom, and leave a progress bar in place when it is done (full, "Ready") rather than removing it. Dialogs that follow one another (a question, then the window it leads to) may each have their own size.
- Every control needs a tooltip (`title`) saying what it does, as a whole sentence (add the keyboard shortcut if it has one). A control with no visible words (an icon, a symbol) or no visible label (an input, a select) also needs it as its `aria-label`, and `ui/src/lib/tooltips.test.ts` fails if not. Text buttons whose label already says it all (Cancel, OK, Back) can go without.
- When the user says "new issue" followed by a problem or idea, they mean: write a GitHub issue about it (`gh issue create`) so we can come back to it later. Do not start debugging or building unless they also ask for that.
